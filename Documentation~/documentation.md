# 文档编写规范

写给所有要修改这个仓库文档的人（包括未来的自己）。目的：让第一次接触这个项目的人也能顺利读懂。

## 语言

- 用平实的陈述句，一句话只说一件事。
- 要说几件事，就拆成列表或表格，不要用分号连成一个长句。
- 不用内部比喻和生造词。技术名词可以用的，但第一次出现时要用一句话解释它是什么（例如：testhost——负责运行单元测试的后台程序）。
- 能具体就不抽象。"测试在 net6.0 上运行"比"测试采用现代运行时"更容易理解。

## 结构

- README 只放概览和上手步骤；细节按主题放在 `Documentation~` 下的对应文件里，README 留链接过去。
- 一个主题一个文件：管线机制、插件设计、测试约定、各转换器（`transformers/` 子目录）各自成篇。
- 并列的内容用表格或列表；有先后顺序的操作步骤用带编号的小节。
- 文档之间的跳转一律用相对链接。

## 与代码保持同步

- 改了路径、工程名、命令或目标框架之后，在同一次改动里把涉及的文档和链接一起更新。
- 文档里的代码示例要能原样照抄运行：命名空间、类名与实际代码一致。

## 提交约定

- **一个提交只做一件事**。重构、修复、文档、格式化互相分开，不要混在同一个提交里；混在一起的历史没法按功能回退或审阅。
- **提交信息使用 Conventional Commits 格式**，即「类型: 描述」。常用类型：`feat`（新功能）、`fix`（修复）、`refactor`（重构）、`docs`（文档）、`test`（测试）、`chore`（工程杂项）。
- **破坏性变更要单独说明**：在提交正文末尾加一段 `BREAKING CHANGE:`，写清楚改了什么、使用者需要怎么做。这类变更发布时需要提升主版本号。
- **提交前自查三件事**：用 `git diff` 逐行看过全部改动；`dotnet format` 通过（命令见 README）；`dotnet test` 全部通过。然后再提交。
